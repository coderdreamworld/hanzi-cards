## 一、原交互中具体出了什么问题

复核依据为实际会话日志：`/Users/ping/.zcode/cli/rollout/model-io-session_3e6164f296424eace65a1ef5b6322551.jsonl`。

### 1. 点名集合执行错误

用户要求生成 14 张确认卡：

`爸、妈、叔、医、孩、飞、买、老、不、和、有、用、当、许`

实际却生成了 23 张：

`拉、群、别、肚、己、又、为、会、见、禾、可、穿、法、孩、巴、妈、叔、医、老、买、不、和、许`

精确差异是：

- 漏掉 5 张：`爸、飞、有、用、当`
- 多做 14 张：`拉、群、别、肚、己、又、为、会、见、禾、可、穿、法、巴`
- 只有 9 张重合：`妈、叔、医、孩、买、老、不、和、许`

旧记忆曾把这次错误写成“只漏了爸、混入 13 张”，与日志不符，现已纠正。

### 2. 把诊断问题误当成修改授权

用户问“`法`为什么四只手？昨天有叫你改吗？”，这是要求解释和追责，不是授权继续编辑。但原执行在没有确认修改范围的情况下直接改了`法`。这是“没让改的又改了”最明确的一例。

### 3. 修改入口与最终状态不唯一

历史操作同时涉及主题模块、迁移脚本、临时覆盖块、生成后的大 HTML 和已经删除的旧 `kebiao_*` 路径。部分命令依靠正则修改大段 SVG 字符串，且串联命令没有在前一步失败时立即停止。这会造成：

- 以为改了，实际改到失效路径或被后续覆盖；
- 源模块与最终 HTML 不一致；
- 一次公共组件修改影响多张未点名卡；
- 失败后仍继续构建，产生“看起来成功”的结果。

### 4. 旧自检存在假绿

旧手臂扫描器提取出的颜色不含 `#`，却拿它和带 `#` 的白名单比较，导致人物头部长期统计为 0；同时只扫描了 395 张模块卡，不是当前最终解析出的 402 张卡。因而“通过”不能证明没有多手、多臂问题。

### 5. 缺少“修改集合必须等于点名集合”的硬约束

旧构建只校验字数和覆盖关系，没有逐卡比较修改前后的组别、文案和插画哈希；公共 `kid()` 等组件一旦改动，还可能扩散到大量卡片。根因不是单次粗心，而是流程里没有可失败的范围断言。

## 四、以后如何保证“点哪张，只改哪张”

项目新增 `识字卡片_修改范围.py`，以最终解析出的逐卡哈希为基准，比较 `group`、`position`、`content`、`art` 四个字段。标准流程是：

```bash
python3 识字卡片_修改范围.py begin 爸 飞
# 只修改点名卡
python3 识字卡片_修改范围.py check
python3 识字卡片_构建.py
python3 识字卡片_修改范围.py finish
```

混合任务按卡片分别授权，例如：

```bash
python3 识字卡片_修改范围.py begin 爸 的:art,content 条:content
```

规则是“实际变更卡集合必须与用户点名集合完全相等”：

- 多改一张：失败；
- 漏改一张：失败；
- 改了未授权字段：失败；
- 变更卡片顺序：也会作为未授权字段失败；
- 模板、构建器、字库、公共素材库和范围锁脚本是全局保护文件，普通单卡任务中修改会失败；
- 有活动范围时：构建器自动先检查，通过后才写正式 HTML；
- 无活动范围时：只允许与现有成品字节一致的幂等重建，任何新变化都拒绝写入；
- `begin` 还会先确认源码与正式 HTML 一致，不能先误改、再事后补开范围；
- 正式 HTML 只允许由 `识字卡片_构建.py` 生成，不再直接手改。

项目级 `AGENTS.md` 还明确规定：提问、举例、质疑和提到某张卡都不自动等于修改授权；公共组件只有在证明最终输出仍只影响点名卡时才能修改；迁移脚本不得作为日常修改入口。
